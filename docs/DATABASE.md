# Initial database design

> This describes the preserved PASS 1 foundation. PASS 2 adds password hashes, revocable sessions, login throttling, one event per organizer, immutable rubric/submission snapshots, explicit claims and leased evaluation jobs. See [PASS 2 schema changes and operations](PASS2_REPORT.md) for current guarantees and limits. Existing financial tables and the isolated PayPal spike are unchanged.

All application tables use UUID primary keys. Mutable records have `created_at` and `updated_at` as timezone-aware timestamps; audit events have only `created_at`. Defaults are generated by PostgreSQL. Drizzle sets `updated_at` on application updates; direct SQL writers must set it explicitly. Foreign keys use restrictive deletion so history is not silently cascaded away.

| Table | Purpose and important constraints |
| --- | --- |
| `organizer_users` | Organizer identity records, without authentication. Email is unique case-insensitively. |
| `hackathon_events` | Organizer, unique slug, deadline, draft/open/judging/completed state, nonnegative integer-cent USD budget. |
| `rubric_versions` | Event-scoped versioned criteria JSON. Positive version; unique event/version. |
| `submissions` | Event, project/team, canonical public GitHub URL, full lowercase 40-character commit SHA. Unique repository per event. |
| `evaluation_runs` | Submission, rubric, status, idempotency key and optional model/prompt/evidence version provenance. Composite foreign keys keep submission and rubric in the same event. No worker implemented. |
| `evidence` | Run-linked source URI/path, optional hash/excerpt, method, status and limitations. Defaults to `NOT_EVALUATED`. |
| `findings` | Run-linked criterion and summary with a required evidence reference from that same run. Defaults to `UNVERIFIED`. |
| `assessments` | Versioned scores and rationale for a run and its submission/event. Finalized status requires an organizer and timestamp. |
| `awards` | Event/submission assessment, unique title per event, revision, recipient, positive integer cents, USD only. Assessment must belong to the same submission/event. |
| `award_approvals` | Explicit organizer approval of exact award revision, assessment, amount, currency and recipient. One approval per award revision; requires a finalized assessment. |
| `payouts` | Sandbox-only durable intent tied to its approved award. Unique award, approval, sender batch/item and external item identifiers. Success requires an external item ID and reconciliation timestamp. No dispatch or reconciliation code. |
| `audit_events` | Event/actor links, action, entity reference and structured metadata. Entity reference is polymorphic, without a foreign key; event and actor have foreign keys. |

Indexes cover common foreign keys, evaluation/payout status and audit chronology. JSON columns validate their outer array/object shape where relevant; full rubric and score semantics require later application validation. Timestamps do not establish workflow order by themselves.

## Approval and payout boundaries

An approval uses a composite foreign key to the exact award terms. Once referenced, PostgreSQL blocks changing those award terms or reverting its assessment to draft. Future revision/revocation logic must explicitly handle approvals and payout history in a transaction; no editing API exists yet. A payout must refer to an approval for the same award. One intent per award and stable unique sender identifiers prevent creating a second dispatch record for retries. This foundation intentionally does not model replacement payouts.

`succeeded` only has structural prerequisites in the database. The future reconciliation service must establish actual PayPal item-level success; database fields alone cannot prove a transfer occurred. There are no triggers or tools that initiate a payout.

## Safeguards deferred to later passes

The schema is a foundation, not a complete financial or authorization layer. Before implementing any mutation or payout service, add and test:

- Authentication and organizer authorization for every mutation, plus request-forgery defenses.
- Transactional event-budget enforcement with appropriate locking; individual nonnegative checks do not enforce aggregate award totals.
- Immutable submission/rubric/assessment snapshots, allowed status transitions, approval revocation rules and append-only audit permissions. Version numbers alone do not prevent direct SQL edits to content.
- Full rubric/score validation, recipient validation, canonical repository URL validation and bounds on supplied evidence. Stored URIs never authorize network access.
- Permanent payout intent/reconciliation rules, timeout handling and credential isolation. Provider IDs are evidence only after verified provider responses.
- Data retention and access rules for recipients and other personal information; audit metadata must exclude secrets.

No future safeguard is presented as a functioning PASS 1 integration. The preserved PayPal spike is not imported by any root application module.
